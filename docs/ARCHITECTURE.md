# 構成と最適化の方針

更新日: 2026-09-24

## リポジトリの境界

- `kakeibowebapp`: React / Material UI / IndexedDB / PWAと、静的配信用nginx。
- [`kakeibo`](https://github.com/Akikan987/kakeibo): FastAPI / PostgreSQL / OCR / 管理画面 / バックアップ。
- Androidクライアントは2026-08-31に廃止済み。現在のAndroid・iPhone向けクライアントはこのWeb/PWA版。

独立したビルド・運用手順を維持するため、今回はモノレポ化や公開URLの変更を行わない。データ形式を変えない処理単位の分離から進める。

```text
src/
  App.tsx                 タブ・画面遷移
  store.tsx               Reactの状態・操作・認証と同期の調整
  db.ts                   IndexedDBのスキーマ・初期値・読み出し
  api.ts                  HTTPとサーバー形式への変換
  sync/
    types.ts              同期する10テーブルの型と一覧
    records.ts            同一レコード判定・LWWの純粋関数
    local.ts              全件読み取りとトランザクション内マージ
  domain/
    ledger.ts             月次集計・割り勘索引・メンバー残額
  payments.ts             引落予定・プリペイド計算（既存の純粋関数）
  receipt.ts, splits.ts    レシート候補照合・均等割り（既存の純粋関数）
  screens/, components/   画面・UI部品
tests/                    業務計算・同期・IndexedDB回帰テスト
public/pr/                紹介サイト（PWA事前キャッシュ対象外）
scripts/                  アイコン・紹介画像の生成と確認
docs/                     設計・検証記録
```

`domain/`と`sync/records.ts`にはReactやHTTPの副作用を持ち込まない。新規の集計ロジックは画面やstoreに埋め込まず、純粋関数とテストを追加する。既存のCRUDはまだstoreに残しており、すべての分割を完了したわけではない。

## 同期の安全性と省データ化

2026-07-30に時刻ベースの差分同期で取りこぼしが起き、全件同期へ移行した経緯がある。今回は`since: 0`と削除済みレコードを含む全件送信を維持する。

1. IndexedDBの10テーブルを読み取りトランザクションで取得する。
2. `POST /sync`へ全件と`omit_unchanged: true`を送る。
3. サーバーは全件を照合し、端末が既に持つ**全フィールドが同一の行だけ**返信から省く。未取得・変更・削除・旧形式で欠けたフィールドは返す。
4. 端末は返信対象のIDだけを読み、ローカルより新しい行、または同時刻で内容の異なる行を一括反映する。読み取りと書き込みは同じトランザクション内で行い、失敗時は全体をロールバックする。
5. 再読み込みした配列が同一内容ならReactの参照を維持し、不要な集計の再計算を減らす。

旧サーバーは追加フラグを無視して全件を返すため、新Webでも動く。旧Webはフラグを送らず、従来の全件応答を受け取れる。返信の空配列は「削除」ではなく「反映する行なし」。物理削除や端末DBの初期化はしない。

API側の契約と検証は[サーバーの同期設計](https://github.com/Akikan987/kakeibo/blob/main/server/docs/SYNC.md)を参照。

## 2026-09-24の検証結果

個人情報のない合成データと一時DBによる測定:

| 対象 | 従来 | 改善後 |
|---|---:|---:|
| 変更なし明細1,000件の応答JSON | 271,005 bytes | 233 bytes |
| 同応答をgzipしたサイズ（圧縮試算） | 約15.7 KB | 約160 bytes |
| 1,200件の既存行照会SELECT | 1件ずつ1,200回 | 500件単位で3回 |
| 同一応答のIndexedDB更新 | 対象全行を書き直し | 0行 |

削減率は**応答だけ**の値で、アップロードやHTTPヘッダーを含む総通信量ではない。共有割り勘の`debts`は毎回返すため、実際のサイズは利用状況で異なる。アップロードはまだ全件であり、データ件数に比例する。アプリ本体の事前キャッシュは約763 KiBのままで、今回の主対象は繰り返し発生する同期・保存・集計処理。

- API38件: 旧形式互換・10テーブル往復・別端末の古いレコード・所有者境界・削除・通信量・SQL照会回数など。APIテストはサーバー側の一時PostgreSQLで実行。

## 次の検討対象

- 上り通信の差分化には、端末時計ではなくサーバー側リビジョンと再取得・復旧手順が必要。今回の省略フラグだけで代用しない。
- 削除済み行の整理は、長期間オフラインの端末との整合性設計後に行う。
- LWWは引き続き端末の`updatedAt`に依存し、時計が進んだ端末の競合まで解決するものではない。
- storeの認証・編集操作は回帰テストを増やしながら段階的に切り出す。

実装時に確認した一次資料: [Dexieのトランザクション](https://dexie.org/docs/Dexie/Dexie.transaction())、[SQLAlchemyのORM SELECT](https://docs.sqlalchemy.org/en/20/orm/queryguide/select.html)。
